00 — Access Philosophy

What You Can and Cannot See — And Why

The Super Admin portal is a business operations tool, not a surveillance system. The line is drawn clearly: you can see everything about how the platform is being used and whether it's working correctly. You cannot see the content of what families are saying to each other. That content is protected, and your ability to resolve support issues doesn't require reading it.

✓ What You Can Access
Everything needed to run the business and resolve support issues
  • User accounts — name, email, plan, signup date, last login, subscription status
  • Payment history — charges, refunds, failed payments, Stripe transaction IDs
  • Report metadata — which reports were generated, when, by whom, what was downloaded, SHA-256 hash of the output
  • Platform activity counts — messages sent (count only), exchanges logged, expenses tracked, reports generated
  • ARIA flag metadata — flag rate %, severity distribution, acceptance rate — per user, not per message
  • KidComs call metadata — call log, duration, participants, flagged call count — not call content
  • Support ticket history for any user
  • Account status — active, suspended, warned, pending deletion
  • Subscription and tier changes with timestamps
  • Login history — timestamps and approximate location (city/state)
  • Grant code status — issued, activated, expired, by whom (anonymized)
  • Case existence — that a case exists between two users, case ID, plan tier, creation date
  • Report generation audit — confirmed that a specific report was generated and downloaded
  • Agreement completion status — what % of sections are signed (not the content)
  • Exchange compliance % per case — not GPS coordinates in detail
✗ What You Cannot See
Protected regardless of support need — by design, not by accident
  • Message content between co-parents — any individual message, ever
  • ARIA rewrites — what ARIA suggested for a specific message
  • Attorney-client privileged communications (Professional Messaging)
  • KidComs call audio, video, or transcripts
  • SharedCare Agreement section content — what was written in any section
  • Individual GPS coordinates from custody exchanges
  • Individual expense amounts or descriptions — only totals and counts
  • Court document content uploaded by users
  • ARIA intake session content — what a client told ARIA before an attorney meeting
  • Children's profiles beyond name and age (no medical, school, or preference data)
  • The actual content of any generated PDF report — only confirmation it was generated
  • Specific flag reasons on individual messages — only aggregate flag category distributions
⚠

If a support issue requires reading message content — it escalates to legal/compliance review, not admin access. The admin portal is designed so that 95%+ of support issues can be resolved without ever needing to see message content. The 5% that can't are handled through a formal escalation path with attorney review.

The Admin Action Rule

Every single action taken in the Super Admin portal is written to audit_logs with the admin's user ID, the action taken, the target user/case/record, and a timestamp. This cannot be disabled. If you look up a user's payment history, that lookup is logged. If you reset a password, it's logged with a required reason field. If you suspend an account, it's logged with a required note. The audit trail protects both the users and the admins.

03 — Report Verification

"They Said a Report Was Wrong" — How to Verify

The most common support scenario for reports: a parent or attorney says a report was generated, something was wrong, or they can't find their download. You don't need to see the report contents to resolve this. The audit trail tells you exactly what happened.

✓

The key principle: You can verify that a report was generated, when it was generated, what it contained in terms of metadata (date range, case ID, type, page count), whether it was downloaded, and what the SHA-256 hash was. You cannot open the report or read its contents. That's enough to resolve every common report support issue.

Report Audit View
Look up any report ever generated on the platform
Metadata Only
What You Can See Per Report
  • Report ID (system-generated UUID)
  • Report type (e.g., "P-6 · Court Evidence Package")
  • Generated by (user name + role)
  • Generated at (exact timestamp)
  • Family file / case ID this report covers
  • Date range the report covers
  • Format (PDF / Word / JSON)
  • Page count
  • SHA-256 hash of the output file
  • First downloaded at (timestamp + IP city)
  • Total download count
  • Last downloaded at
  • Signed URL expiry date (when the download link expires)
  • Tier required vs. user's tier at time of generation (confirms they had access)
  • Payment verified at time of generation (Y/N)
Common Support Scenarios + Resolutions
  • "I ran the report but can't download it" — Look up report by user. Check signed URL expiry. If expired, generate a new download link (admin action, logged). If never downloaded, confirm report completed. Check job_status field.
  • "The report was wrong / missing data" — Check report metadata: date range, sections included, case ID. Verify that the case had activity in the date range. If data was missing from the source (e.g., exchanges not logged), show user what data existed at time of generation. Cannot regenerate with different content — the hash proves what the report said.
  • "I paid for Complete but the report said I need to upgrade" — Check user's subscription tier at report generation timestamp. Check payment status at that time. If the user was on Complete and the system still blocked them, escalate to engineering with the report ID and user ID.
  • "The attorney says the SHA-256 doesn't verify" — Look up the report, copy the stored hash from the audit record, and provide it to the attorney to compare against the PDF. If they match, the PDF is authentic. If they don't, escalate immediately — this is a data integrity event.
  • Actions: Generate new signed download URL · Confirm report metadata · Look up payment status at time of generation · Escalate to engineering with report ID · Create support ticket linked to report

04 — Support Tickets

Creating, Managing, and Resolving Issues

Every support interaction goes through a ticket. Tickets can be created by users (in-app), by you on behalf of a user, or auto-generated by platform alerts (e.g., failed payment, flagged KidComs call). Every ticket is linked to a user, has a priority level, and has a full internal conversation thread that's never visible to the user.

Ticket Fields
What every support ticket contains
  • Ticket ID: Auto-generated (TKT-XXXXX) — referenceable
  • Created by: User self-service / Admin on behalf / System auto-generated
  • Created at: Timestamp
  • User: Name, email, tier, role — linked to their full user profile
  • Category: Billing · Report Issue · Account Access · KidComs · ARIA · General · Feature Request · Bug Report
  • Priority: High (response SLA: 4hrs) · Medium (24hrs) · Low (48hrs)
  • Status: Open · In Progress · Waiting on User · Escalated · Resolved · Closed
  • Assigned to: Admin team member handling it
  • User-facing thread: Messages visible to the user
  • Internal notes: Admin-only notes — never shown to user
  • Related records: Link to report ID, transaction ID, case ID, or event that prompted the ticket
  • Resolution summary: What was done to resolve it (populated on close)
  • Time to first response / Time to resolve: Auto-calculated
  • Actions: Reply to user · Add internal note · Change priority · Change status · Escalate to engineering · Link to related record · Assign to team member · Close ticket

06 — KidComs Oversight

Flagged Calls — Metadata Review Only

When the KidComs AI moderation flags a call, it creates a record in the system and generates an auto-ticket. Your job is to review the metadata of the flag — not the call content — and determine if any action is needed. If the flag indicates a genuine safety concern, you escalate to legal. You do not access call audio or video from the admin portal.

⚠

Admin does NOT have access to KidComs call audio, video, or transcripts from this portal. Accessing call content requires a formal legal process (court subpoena or both parents' written consent). The metadata review described below is sufficient to determine whether an escalation is warranted without accessing the content itself.

KidComs Flagged Event Review
What you see and what you can do
Metadata Only
Flag Metadata (Visible)
  • Call date and time
  • Call duration (total and duration of flagged segment)
  • Participants: which child, which parent/Circle contact was on each end
  • Flag type: inappropriate_content · hostile_language · third_party_interference · child_distress · safety_concern
  • Flag severity: 1 (informational) · 2 (review needed) · 3 (urgent) · 4 (immediate action)
  • AI confidence score on the flag (0–100%)
  • Timestamp within the call where flag occurred (e.g., "4 min 22 sec into call")
  • Whether parents were notified automatically (Y/N)
  • Whether an evidence clip was extracted and SHA-256 hashed (Y/N)
  • Review status: Pending · Admin Reviewed · Escalated · Cleared
Review Actions
  • Mark as Reviewed — Cleared: Flag was reviewed based on metadata and context; no action needed. Add note explaining why. Both parents notified that the flag was reviewed and cleared.
  • Mark as Reviewed — Action Needed: Flag warrants follow-up. Creates or links to a support ticket. Admin can contact the relevant parent directly.
  • Escalate to Legal: Flag severity 3–4 or any flag involving child_distress or safety_concern. Triggers formal escalation. Admin cannot access the evidence clip — legal team coordinates with law enforcement if needed.
  • Notify Parent(s): Send a notification to one or both parents about the flag. Use standardized language: "A KidComs session on [date] was flagged by our AI moderation system. Our team has reviewed the event and [action taken]."
  • Suspend KidComs for this case: Emergency action — disables KidComs calls for the family file while investigation is in progress. Both parents are notified.
  • Access or play the evidence clip
  • See the content of what was said

08 — Platform Operations

System-Level Controls for a Non-Technical Operator

The operational controls that don't require engineering to execute — maintenance notices, user communications, feature flags, and account-level overrides. These are the levers a customer success manager or operations lead would need day-to-day.

Communications
Reach users on the platform
  • Platform-wide announcement banner — appears at top of app for all users. Set text, duration, type (info/warning/maintenance). No engineering needed.
  • Send in-app notification to a user — custom message to any user, logged with reason
  • Send email to a user — uses SendGrid, from support@find-commonground.com, logged
  • Send email to a user segment — "all Plus users in LA County" or "all attorneys who haven't activated an intake in 30 days"
  • Maintenance window notice — schedule a downtime notice to appear in-app 24hrs before
  • All communications sent from the admin portal are logged with the sending admin, recipient(s), and timestamp. Users can see their notification history in their account.
Account Controls
User-level overrides and safety actions
  • Suspend account — blocks login immediately. User sees "Your account has been temporarily suspended. Contact support." Requires reason + confirmation. Reversible.
  • Unsuspend account — restore access. Logged with reason.
  • Force password reset — next login requires new password. Used when account compromise suspected.
  • Revoke all active sessions — logs user out of all devices immediately. Used for security events.
  • Delete account (GDPR) — permanent. Multi-step confirmation. Logs deletion in compliance record. Cannot be undone. Legal review required before execution.
  • Add account flag / warning — internal note visible to all admins on this user's profile. Not visible to user. Example: "User has disputed 3 charges — require manager approval for future refunds."
Feature Flags (Non-Technical)
Toggle features per user or tier
  • Enable/disable KidComs for a family file — emergency toggle for safety situations
  • Override tier feature access — grant a Free user temporary Plus features for support investigation or goodwill. Time-limited, logged.
  • Enable/disable ARIA for a specific case — in the rare case ARIA is behaving incorrectly for a specific case, disable it while engineering investigates
  • Unlock report generation — if a report failed due to a system error and user is on the correct tier, unlock manual regeneration
  • Feature flag changes are time-limited (max 30 days) and require a reason and an associated ticket ID. They expire automatically and send an alert when they do.
09 — Admin Audit Log

Every Admin Action is Recorded

The admin audit log is the record of everything done from this portal. It cannot be deleted, filtered out, or modified. Every admin sees their own log and superusers see all admin logs. This is what you'd produce if a user ever asked "why was my account suspended?" or "did anyone from CommonGround access my account?"

Admin Audit Log — Fields + View
Never Deletable
Every Audit Entry Contains
  • Admin user ID and display name
  • Action type (e.g., "issued_refund", "suspended_account", "viewed_user_profile", "generated_download_link")
  • Target entity type and ID (user_id, case_id, ticket_id, report_id, etc.)
  • Target entity display name (e.g., "Sarah M." — for human readability)
  • Before state (for changes — e.g., previous plan tier)
  • After state (e.g., new plan tier)
  • Reason field (required for all write actions — free text, min 10 chars)
  • Associated ticket ID (if action was taken in context of a support ticket)
  • IP address of admin at time of action
  • Timestamp (UTC)
  • Read actions (viewing a user profile, looking up a report) are logged at the "info" level. Write actions (refunds, suspensions, plan changes) are logged at "action" level with before/after state. Destructive actions (deletions, permanent changes) are logged at "critical" level with a confirmation hash.
Actions That Require a Reason Field
  • Issuing a refund
  • Applying an account credit
  • Changing a user's subscription plan
  • Suspending an account
  • Unsuspending an account
  • Deleting an account
  • Extending a trial period
  • Impersonating a user session (requires reason + manager approval)
  • Generating a new download link for a report
  • Disabling KidComs for a case
  • Applying a grant code manually
  • Revoking all user sessions
  • Sending a bulk email to a user segment
  • Reason fields are permanent. They cannot be edited after submission. Think before typing.

The One Rule That Governs This Entire Portal

If you ever ask yourself "can I look at this to help a user?" — the answer is almost certainly yes, and the system is designed to let you do it. If you ever ask yourself "should I look at this?" — that's a different question. The audit log means you should never look at anything you wouldn't be comfortable explaining in a support ticket note, to a user, or to a regulator. The portal gives you significant access. The audit log ensures that access is always accountable.
