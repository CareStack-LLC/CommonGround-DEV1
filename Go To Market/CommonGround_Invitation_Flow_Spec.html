Single-Parent Activation — No Co-Parent Dependency
Problem: Platform deadlocks if co-parent hasn't joined — client can't do anything, gives up immediately
⚠

This is a silent killer. If the invited client activates but their co-parent doesn't join within 48 hours, the client hits empty screens everywhere and concludes "this doesn't work." They tell their attorney. The attorney stops recommending it. One unactivated co-parent kills your referral chain.

What Works Without Co-Parent

  • ARIA message drafting — client can prepare messages even before co-parent joins
  • Schedule builder — client can build their proposed schedule and it waits for co-parent review
  • Expense logging — client can log any expense immediately
  • SharedCare Agreement drafting — start sections, invite co-parent to review later
  • Document uploads — court orders, agreements, any PDFs
  • Attorney can already see the case, even before co-parent joins
  • ARIA intake completion (if not already done)

What Requires Co-Parent

  • Two-way ARIA messaging — needs someone to send to
  • Exchange scheduling — both parents need to confirm
  • SharedCare Agreement approval — dual signature required
  • ClearFund expense requests — co-parent must receive and approve
  • KidComs calls — dual-parent consent is a legal requirement

For everything in this list: show a clear "Waiting for [Co-Parent Name] to join" state with a resend invite button. Never show a blank screen.

Co-Parent Invitation — Automated

  • When client activates, automatically queue a co-parent invitation for 2 hours later
  • Co-parent invitation says: "[Client name]'s attorney has set up CommonGround for your custody case" — not just a generic invite
  • Co-parent gets the same magic link flow — no friction
  • Attorney is notified when co-parent is invited and when they activate
  • If co-parent hasn't activated in 72 hours, send one reminder automatically

from fastapi import APIRouter, Request router = APIRouter() @router.post("/webhooks/sendgrid/events") async def handle_sendgrid_event(request: Request, db: AsyncSession = Depends(get_db)): events = await request.json() for event in events: case_id = event.get('case_id') # From custom_args we set when sending email_type = event.get('email_type') event_type = event.get('event') # delivered, open, click, bounce if not case_id: continue if event_type == 'open': await update_invitation_status(case_id, 'email_opened', db) elif event_type == 'click': await update_invitation_status(case_id, 'link_clicked', db) elif event_type == 'bounce': await update_invitation_status(case_id, 'bounced', db) await alert_attorney_bad_email(case_id) # Immediate portal notification return {"received": len(events)}
06 — Case Creation

Four Entry Paths — One Case

The attorney shouldn't feel like they're doing data entry. Every case entry path ends in the same place — a populated case file ready to send invitations — but starts from wherever the attorney already is. The goal is: least new work possible to get a case into CommonGround.

The Rule for All Four Paths

An attorney should be able to invite a client within 3 minutes of starting any of these flows. If any path takes longer than 3 minutes from start to "invitation sent," it needs to be simplified. Every field beyond the minimum required should be optional and fillable later — never a blocker to sending the invite.

✏️
Path A — Quick Create (Manual)
30 seconds Always available
Attorney types the bare minimum. Everything else is filled in later by the client or auto-populated from the intake. This is the default path for every new case.
Required Fields Only
  1. Client name (first + last)
  2. Client email or phone number
  3. Co-parent name (optional at creation)
  4. That's it — click "Create Case + Send Invite"
→

Everything else — children, custody %, court dates, agreements — populates from the ARIA intake the client completes after they activate. The attorney doesn't fill in the case file. The client does, guided by ARIA.

🤖
Path B — From ARIA Intake
Auto-populate Recommended
When an attorney sends an ARIA intake link and the client completes it, all extracted data auto-populates into a case file. Attorney reviews the AI Summary and clicks "Convert to Case."
What Gets Auto-Populated
  1. Both parent names from intake responses
  2. Children names and ages extracted by ARIA
  3. Current custody situation (narrative + structured)
  4. Client goals and key concerns (from AI summary)
  5. Recommended next steps (from AI summary)
  6. Co-parent's email if client provided it
★

This is the ideal path. The case is pre-populated before the first meeting. Attorney does zero data entry. The "Convert to Case" button on the ARIA Summary screen should be large and prominent.

🔗
Path C — Import from Clio / MyCase
OAuth Phase 2
Attorney connects their Clio or MyCase account once. Then for any matter, they click "Add to CommonGround" and the case is created with client data already populated.
Implementation Notes
  1. OAuth 2.0 connection from attorney Settings → Integrations
  2. Pull: Matter name, client name, client email, opposing party
  3. Do NOT pull: billing data, time entries, attorney notes (privilege)
  4. On import: create case, pre-fill client info, queue invitation
  5. Clio API v4 endpoint: GET /api/v4/matters/{id} with contacts
  6. MyCase API: GET /api/v1/cases/{id} with client associations
Env Vars to Add
CLIO_CLIENT_ID=your-clio-app-id CLIO_CLIENT_SECRET=your-clio-secret MYCASE_CLIENT_ID=your-mycase-app-id MYCASE_CLIENT_SECRET=your-mycase-secret # Redirect URI registered in both portals: # https://find-commonground.com/integrations/callback
📄
Path D — Upload Court Document
OCR + AI Parse Phase 2
Attorney uploads an existing custody order, divorce decree, or FL-300 form. ARIA extracts parent names, children, custody terms, and court dates to pre-populate the case.
Implementation Notes
  1. Accept PDF upload on "New Case" screen
  2. Run through Textract (AWS) or PyMuPDF for text extraction
  3. Pass extracted text to Claude with structured extraction prompt
  4. Claude extracts: party names, children, custody schedule, court dates
  5. Attorney reviews extracted fields — edits anything wrong
  6. Confirm → case created → invitations queued

→

07 — Database Changes

Schema Additions for the Invitation System

Three new tables and additions to your existing FamilyFile model. Use Alembic to generate the migration after adding SQLAlchemy models.

New Table: case_invitations
-- Tracks every invitation sent from an attorney CREATE TABLE case_invitations ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), case_id UUID REFERENCES family_files(id), attorney_id UUID REFERENCES users(id), invitee_email TEXT NOT NULL, invitee_name TEXT, invitee_role TEXT -- 'client' | 'coparent', magic_link_token TEXT UNIQUE, status TEXT DEFAULT 'pending', -- pending | delivered | opened | clicked | activated | bounced | expired email_sent_at TIMESTAMPTZ, email_opened_at TIMESTAMPTZ, link_clicked_at TIMESTAMPTZ, activated_at TIMESTAMPTZ, resend_count INT DEFAULT 0, sendgrid_message_id TEXT, -- for webhook matching created_at TIMESTAMPTZ DEFAULT NOW() );
New Table: case_events (Realtime)
-- Append-only event log — Supabase Realtime broadcasts inserts CREATE TABLE case_events ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), case_id UUID REFERENCES family_files(id), event_type TEXT NOT NULL, -- client_activated | coparent_activated | email_opened -- message_sent | aria_flag | court_date_added | doc_uploaded user_id UUID REFERENCES users(id), metadata JSONB DEFAULT '{}', created_at TIMESTAMPTZ DEFAULT NOW() ); -- Enable Realtime on this table in Supabase dashboard -- Table → Replication → Toggle on case_events -- New Table: attorney_notifications CREATE TABLE attorney_notifications ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), attorney_id UUID REFERENCES users(id), type TEXT NOT NULL, case_id UUID REFERENCES family_files(id), title TEXT, body TEXT, is_read BOOLEAN DEFAULT FALSE, action_url TEXT, created_at TIMESTAMPTZ DEFAULT NOW() );
Updates to Existing family_files Table
-- Add these columns to your existing FamilyFile model: ALTER TABLE family_files ADD COLUMN IF NOT EXISTS client_a_status TEXT DEFAULT 'pending', -- pending | invited | active client_a_activated_at TIMESTAMPTZ, client_b_status TEXT DEFAULT 'pending', client_b_activated_at TIMESTAMPTZ, case_entry_source TEXT, -- manual | aria_intake | clio | mycase | court_doc invitation_status TEXT DEFAULT 'not_sent'; -- not_sent | pending | partial | complete
08 — Implementation Order

What to Build First, Second, and Third

This is the sequence that gets you to your first attorney demo as fast as possible. Don't build Path C or D before Fix #1–5 are done. An attorney-branded invitation with magic link auth is worth 10x more than a Clio integration for your first 10 pilots.

The 48-Hour Test — Do This Before Your First Demo

Create a test attorney account. Create a case with your own phone number / personal email as the "client." Click "Send Invitation." Open the email. Click the button. Complete the welcome screen. Stop the clock. If it took more than 3 minutes from invitation sent to being on the platform — find the friction and remove it. If the email looked like it came from CommonGround instead of a named attorney — fix the From Name. This test is the only thing that tells you if the champion model will actually work. Run it at least 5 times before your first pilot attorney sends their first real invitation.
